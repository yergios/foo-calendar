# Changelog

## Unreleased

### Added

- **Security headers.** The page the app serves carries a strict Content-Security-Policy: scripts only from the app itself plus its one inline configuration script, allowed by a hash computed at startup; connections and frames only to the app and the identity provider in `Auth:Authority`; no plugins; no framing by other sites. Every response carries `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. If a reverse proxy sets its own policy, remove it there: the app's must reach the browser unchanged.
- The holiday sync and the retention sweep report traces and metrics over OpenTelemetry, under the `FooCalendar` source and meter: a span per sync run and per country, runs, failed countries and duration; a span per sweep and the rows it deleted per table. See [deployment](https://github.com/yergios/foo-calendar/blob/master/docs/deployment.md#the-apps-own-spans-and-metrics) for the names.
- **Sign out** in the header of the calendar, profile and admin pages. It ends the session with the identity provider when the provider advertises an end-session endpoint, and removes everything the app stored in the browser, interface preferences included. Register `Auth:PostLogoutRedirectUri` (default `/`, resolved like `Auth:RedirectUri`) with your provider as an allowed post-logout redirect.
- `GET /api/absences` and `GET /api/bank-holidays/catalog` refuse a range that ends before it starts or spans more than 366 days, with a 400. The app itself never asks for more than a year.
- `Retention:AuditEntryDays` (365) and `Retention:AbsenceDays` (off) delete data that has outlived its purpose, swept daily. Absences are left alone by default — looking back over previous years is what the calendar is for. `0` keeps a table forever.
- [`docs/data-protection.md`](https://github.com/yergios/foo-calendar/blob/master/docs/data-protection.md): every personal-data field the app stores, everywhere data leaves, and what is the deploying team's own responsibility.
- `Team:OrgName` puts your team's name in the header.
- Per-job permissions instead of a single admin role: `PeopleManage`, `ReportsRead`, `HolidaysSync`, and `AuditRead`, each configured under `Auth:Permissions` (the claim values that grant it) and enforced by a policy of the same name. The app refuses to start if a permission is left with no values.
- An audit log, readable at `/admin` with `AuditRead` or from `GET /api/admin/audit`. It records profile creates/updates/deletes, bulk imports, deleted absences, every hand edit to a manual bank holiday, and hand-triggered syncs — with who did it and when. Append-only, and a person's entries outlive their profile. `/healthchecks/detail` also requires `AuditRead`.
- `Auth:DevUser:GrantAllPermissions` (default on) holds every configured permission in local development, so the dev bypass never drifts as permissions are added. Set it false to browse as a plain member.
- The API describes itself as OpenAPI at `/openapi/v1.json` and serves a [Scalar](https://scalar.com/) reference over it at `/scalar`, with a bearer scheme so calls can be made from the page. On by default in development, `ApiDocs:Enabled` elsewhere — both routes are anonymous, so it is off by default.
- An absence's note is visible only to its author. The team sees the dates and the type; nobody else sees the note, on the calendar, on the admin page, or in the audit log.
- Regions are tracked automatically: picking one on your profile starts syncing that region's public holidays, for the current year and the next. `Team:HomeRegion`, the team's own locality, is required and always synced, never removed even once nobody's home city matches it.
- When the last person in a region leaves or is deleted, that region's bank holidays are deleted too, including manually added ones; a country's nationwide holidays go only once nobody is left in any of its regions, and the home region is exempt. The calendar's region filter and the manual bank-holiday form offer only the regions the team occupies — adding a holiday for anywhere else is rejected.
- The admin sync panel (`HolidaysSync`) can re-run a single region, which is what a region reported as failed needs; `POST /api/admin/bank-holidays/sync` reports `syncedRegions`/`failedRegions` and takes an optional `region` for this. `HolidaysSync` gates only this hand-triggered sync, which calls out to the holiday source and writes in bulk — manually added bank holidays stay everyone's to maintain.
- A new `Appointment` absence type, and an `Other` absence may now optionally be time-based too: a single day with a start and end time instead of a whole-day date range. Any number of time-based absences can share a day; a whole-day absence still takes the day exclusively. `Team:HomeTimeZone`, an IANA timezone id (e.g. `Europe/Zurich`), is required — every time-based absence's start/end time is wall-clock time in this one zone, for every viewer, and every displayed time is labeled with it.
- A "Who's off today" button on the home page lists everyone out today: personal absences plus anyone whose home region has a bank holiday, without listing a person twice for both.
- Arrow buttons alongside the calendar grid page it horizontally by about a viewport's width; holding one down ramps into a continuous scroll instead of repeated clicking.

### Changed

- **The identity provider's endpoints must be on `Auth:Authority`'s origin.** The new Content-Security-Policy lets the page reach only that origin besides its own, so a provider whose discovery document puts the token endpoint on another host fails to sign in, with a `connect-src` violation in the browser console. Most providers serve everything from the issuer's host.
- The API reference no longer loads fonts from, or reports usage to, Scalar's servers, and runs under a policy of its own.
- `/index.html` answers 404. The page is served only as the app's own routes, always with its policy; served straight from disk it carried none.
- **`Auth:Authority` must be an `https` URL outside Development.** The API fetches the keys it validates tokens with from there, so over plain `http` anyone on the path could hand it keys of their own. A deployment whose `Auth:Authority` starts with `http://` no longer starts; the message names the setting. Development still accepts `http`, for a local identity provider.
- **The `Sick` absence type is gone.** An absence's type is visible to the whole team, and "this person is ill" is health data, which carries a much higher bar than anything else here. Record illness as `Other`, which says someone is away without saying why — and keep health details out of the note, which is the one field the app can't reason about.
- Branding is split in two. Colors, fonts and shape are yours to change in `src/Web/src/styles/theme.css` and are compiled in; your team's name and support links are runtime config under `Team:`. The product's own name and mark are neither — they are constants, and the footer attribution is not removable. See TRADEMARK.md.
- `Branding:AppName` is gone; `Branding:SupportUrl` and `Branding:IssueUrl` are now `Team:SupportUrl` and `Team:IssueUrl`.
- The API inlines the sign-in configuration into the page it serves, so the app no longer waits on a config request before it can mount.
- The admin area is split into its own page per section — People, Bank holidays, Audit log — reachable from a left sidebar, each gated by its own permission(s). The sidebar, and the nav item leading to it, shows only what you hold; someone who holds none of them never reaches `/admin` at all.
- The profile page offers every country and region the holiday source knows about, rather than a fixed list. Both fields are searchable, by name or by code, and ignore accents.
- Region and country names come from a bundled CLDR name table, so a region no longer has to be named by hand to be readable.
- The team view now defaults to sorting you first, then everyone else by name, instead of a plain alphabetical list. Sort by Name is still there if you'd rather have that.
- The Sort and Region/year icons, and the admin table's sort arrows and region filter, now show what they do on hover.
- **Email is gone**: no more SMTP relay, per-person `EmailOn…` preferences, weekly digest, or `Person.Email` address field, on the profile form or in bulk CSV import/export. `Email:*` configuration is gone; nothing replaces it.
- **The webhook is gone.** It had no consumer built into the app and nothing here depended on it; if you were posting `absence.*` events somewhere, that integration needs to move to polling `GET /api/absences` instead. `Webhook:*` configuration is gone.

### Removed

- **Absence approvals**, and the in-app notifications that only existed to report on them ([decision record](https://github.com/yergios/foo-calendar/blob/master/docs/decisions/0014-remove-absence-approvals.md)). Every absence is on the calendar, and counts toward totals, the moment its owner saves it; entitlement and approval belong to an HR system. Gone with them: the approvals admin section, the notification bell, `/api/notifications`, `/api/admin/absences/*`, the `status` of an absence, `AbsenceApprovals:Enabled`, the `AbsencesApprove` permission and `Retention:NotificationDays`. The app refuses to start while `AbsenceApprovals:Enabled` is set to anything but `false`, or anything under `Auth:Permissions:AbsencesApprove` is still set, saying the feature was removed.
- On upgrade, the database migration deletes rejected absences (the calendar already hid them), keeps pending ones as ordinary absences, and drops the notifications table. Audit entries recording earlier approvals and rejections stay until retention removes them, and the audit log can still filter by them.

### Fixed

- Opening `/admin` directly, by a bookmark or a reload, no longer fails with "could not load its configuration".
- A request that should carry a body but has none answers 400. It used to be a 500.
- A signed-in request whose token lacks the claim `Auth:ClaimTypes:UserName` names answers 500 on the routes that need to know who is asking, and the logged error names the claim and the setting to change. It used to be a 409, or a profile created with no username.
- `POST /api/admin/people` requires a `username`; a missing or blank one is a 400. It used to create a person with no username, and answer 409 to every later one.
- A year outside 1900 to 2999 on the stats routes, the people list or the holiday sync answers 400. Some used to answer 500.
- The holiday file (`Holidays:Source=File`) refuses an entry with no `region` or no `date`: the file counts as malformed and the sync reports the country as failed. An entry with no date used to be read as 1 January of year 1.
- A server error answers with problem details that say nothing about the exception, in Development as well; the exception is in the log.
- **Bearer token claims are read under the names the identity provider issues them.** The API used to rename the common ones to long-form names on the way in (`sub` became `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier`, `roles` became `http://schemas.microsoft.com/ws/2008/06/identity/claims/role`, and so on), so the `Auth:ClaimTypes` defaults, `sub`, `given_name`, `family_name` and `email`, and claim types such as `roles` listed in `Auth:ClaimTypes:Permissions`, found nothing: no username, no names, no permissions. If you set any `Auth:ClaimTypes` value to a long-form name to work around that, set it back to the name in the token (`sub`, `roles`, `groups`, ...). Left as it is, it now matches nothing, and people signing in lose their username or their permissions without any error.
- An API request no route takes no longer gets the app's page with a 200. A path no route matches answers 404, a method or content type the route doesn't take 405 or 415, each as problem details, and 401 to anyone not signed in. The page itself is served for GET and HEAD only.
- A configuration value inlined into the page the API serves can no longer end its script element: `<`, `>` and `&` are escaped, so a value containing `</script>` stays data.
